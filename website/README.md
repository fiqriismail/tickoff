# Tickoff website

Astro + Starlight generate the user-facing static HTML website. Developer app
build instructions and architecture remain in the [repository README](../README.md).

## Requirements and commands

Use Node.js 24 LTS (at least Node.js 22.23.4) and npm 9.6.5 or later.
Run these commands from this directory:

```sh
npm ci
npm run dev
```

Open <http://localhost:4321/tickoff/>. To validate a production build:

```sh
npm run check
npm run build
npm run check:links
npm run preview
```

Preview also serves <http://localhost:4321/tickoff/>. Search is generated by
Pagefind during the production build, so test search in preview rather than
the development server. Stop either server with Control-C.

The static output is `dist/`. `check:links` starts a loopback-only preview on an
available port, validates every generated HTML page and stylesheet, and stops
the server even if validation fails. It checks internal URLs, fragments, images,
scripts, styles and CSS assets under `/tickoff/`, and requires the generated
Pagefind entry point. External sites are skipped so CI does not depend on
third-party uptime. Browser search and visual checks are still required.

The link checker uses Linkinator. Its `glob` dependency is overridden to the
patched 14.x release because the upstream 13.x range has known denial-of-service
advisories. Reassess the override when upgrading Linkinator; do not remove it
without checking `npm audit` and running link-validation regression checks.

## GitHub Actions and publishing

[The Website workflow](../.github/workflows/website.yml) runs `npm ci`, the Astro
check, the production build and link validation on pull requests and main pushes
that change the website, workflow or app icon. It also supports manual dispatch.
Pull requests only validate; they never upload or deploy a Pages artifact.
Builds have read-only repository permissions and do not persist Git credentials.

**Publishing is off by default.** Upload and deployment require all of:

- A successful validation/build.
- A push or manual run on `main` (never a pull request or another branch).
- The repository Actions variable `PAGES_DEPLOYMENT_ENABLED` set to `true`.

Only the separate deployment job receives `pages: write` and `id-token: write`.
Its `github-pages` environment shows the deployed URL, and deployment concurrency
prevents overlapping publications. Pull-request runs cancel superseded validation.
Actions are pinned to commit SHAs; update the pins deliberately when upgrading.

### First publication (only after owner approval)

1. Review the current landing page, complete guides and refreshed screenshots.
   Merge the approved website branches into `main`.
2. In repository **Settings > Pages**, choose **GitHub Actions** as the source.
   The workflow does not auto-enable Pages or change repository settings.
3. If using protection rules on the `github-pages` environment, allow deployment
   from `main` and configure any required reviewers.
4. In **Settings > Secrets and variables > Actions > Variables**, create the
   repository variable `PAGES_DEPLOYMENT_ENABLED` with value `true`.
5. In **Actions > Website > Run workflow**, select `main` and run it. Subsequent
   relevant pushes to main publish automatically after validation.
6. Verify <https://fiqriismail.github.io/tickoff/> and representative nested
   Guide/Help pages, images, search results, mobile/desktop layouts, keyboard
   navigation, and light/dark appearance. Check the custom 404 recovery too.
7. Only after the public site works, add its live link to the repository README
   and shorten duplicated user-facing material, keeping developer build,
   architecture and release instructions.

To pause future publications, remove the variable or set it to `false`.
This does not unpublish the current site or cancel an already-running deployment;
cancel any active deployment separately if necessary. A failed validation leaves
the previously deployed site unchanged.

Until publication is explicitly approved, keep the deployment variable unset.
The implementation and remaining live verification are tracked in
[#60](https://github.com/fiqriismail/tickoff/issues/60).

## Editing

- Add user guides as Markdown or MDX in `src/content/docs/`. Each page needs
  `title` and `description` frontmatter.
- Maintain Guide and Help navigation in `astro.config.mjs`.
- Guide pages cover getting started, tasks, search/filters, projects, Daily Goals,
  shortcuts and display options. Help covers data/backups, troubleshooting and FAQ.
  Keep command names, destructive-action warnings and current limitations aligned
  with the app implementation; do not describe retained history as an available
  history browser or an undo workflow.
- The product landing page lives in `src/pages/index.astro`; the documentation
  overview lives at `/tickoff/guide/`. Header and footer overrides use the landing
  page layout only at the site root and retain Starlight's defaults for guides.
- Use `src/styles/custom.css` for shared typography and colour tokens.
- `src/pages/404.astro` owns the error page; Starlight's injected 404 route is
  disabled to avoid generating a second route for the same address.
- Place processed content images in `src/assets/` and static files in `public/`.
- Current screenshots live in `src/assets/screenshots/`. Use `AppScreenshot.astro`
  to display matching light/dark images with responsive WebP output, descriptive
  alternative text and a link to the original for readable full-size details.
- Screenshots were captured from test-owned windows with fictional in-memory
  data, not the real database. Capture from the permitted launching tool using
  only the specific window ID; do not capture a whole display or use synthetic
  input. Set appearance on the capture window rather than changing system settings.
- Keep internal Markdown links relative to the current page URL. In Astro
  components, construct local links and public asset URLs with
  `import.meta.env.BASE_URL`, which includes the `/tickoff/` prefix. Do not use
  domain-root links such as `/guide/`.
- Keep `package-lock.json` committed. Use `npm ci` for reproducible installs.

When adding, changing or removing a user-facing app feature, update affected
guides, landing-page descriptions, shortcuts and screenshots in the same change,
as required by [AGENTS.md](../AGENTS.md). Use only isolated fictional data in
screenshots.

Before submitting changes, run the check and build commands, then verify links,
search, keyboard navigation and mobile/desktop layouts in both light and dark
mode using production preview.
